# E-04: event deck E1–E6 and the seed

## Built
- `engine/seed.ts` (new) holds the seeded deck:
  - `deckFor(seed)`, `dealtEvent(seed, week)`, `eventCard(id)` and `assertSeed(seed)`.
  - Level 1 defines only the `demo` seed (ENGINE-DATA-AND-TESTS §1). A random seed is COULD (GM-14). So a seed without a deck in `level1.json` throws `RuleError("unknown_seed")` from `createGame` and `resetGame`. It no longer falls back to the demo deck silently (QA P2 from E-01).
- `engine/events.ts` (new) holds the event rules:
  - **Shown event.** A card is shown when three things hold: the seed dealt it for the current week, its condition holds, and it is not yet resolved.
  - **E5 `gap_open`.** The condition uses the known-ledger forecast (`includeFutureEvents: false`, as the contract says). It still counts resolved events and played cards.
  - **`resolveEvent`.** It records the choice and awards the own or delegated competence milestone (never lowered, capped at 3). E5 `show_cost` sets `loanTermsShown`. It never plays C5 and never uses the week's action.
- **Event overlay** in `engine/forecast.ts`. I extended it and did not add a second one. It now books every effect type:
  - `transaction`: E1 re-payment 8 I, E2-S2 14 XII and E2-C 29 I, E3 15 XII. These rows have `source: "event"` and `eventId` set.
  - `reveal`: E1 `pay_as_is`. The data now carries `ledgerId: "L08"`, and the overlay sets `eventId: "E1"` on the L08 payment that went to the changed account. In the known-ledger view, the effects after the reveal (the 8 I re-payment) stay hidden until 23 XII lies before the current week. The default forecast, which is what `resolveWeek` settles, always includes them as scripted future, the same way it treats E6.
  - `move_invoice`: E6, as in E-02.
  - `reveal_card`: no money effect.
- **Narration signals (QA P2 from E-01).** An event's signal is emitted by the transition that makes the card current, not by resolving it:
  - E2 → `bigProject`;
  - E5 → `loanOffered` with `via: "E5"`;
  - E6 → `lateClient`, with `newDate: "2027-01-22"` while INV-A1 is pending, else `null`.

  The transitions that make a card current are `createGame`/`resetGame` (T1), `resolveWeek` (into the next week; the signal is in `events` and `state.emitted`) and `rewind`, which shows the restored week's card again. `resolveEvent` now emits `[]`.
- `quietWeek` now means a week with no transactions and no resolved event.
- Data checks added in `engine/data.ts`:
  - the demo seed exists;
  - each deck slot's week equals the card's week;
  - no deck has two events in one week;
  - every reveal points to an existing ledger row.

## Proof

- ET-E01 … ET-E09, one `it` each. ET-E07 covers C1, C2 (T1–T4), C3, C4 and C6 hiding E5. It also checks that C6 played in T5 hides E5 and that C2 in T5 (too late) keeps it shown.
- Other checks:
  - demo deck order;
  - `unknown_seed`;
  - `bigProject` fires when E2 is shown, including after a rewind;
  - the `loanOffered` and `lateClient` signals;
  - E5 `show_cost` reveals the non-bank (`N`, `non_bank_lender`) loan without playing it;
  - the fraud row and the known-ledger reveal gating;
  - an event never uses the card action;
  - wrong or repeated choices are rejected;
  - inputs are never mutated.

`pnpm check` is green: typecheck, lint, 67 tests, build.

## API changes
No signature changes. Additive changes:
- `RuleErrorCode` gains `"unknown_seed"`.
- The `reveal` effect in `level1.json` and its schema gains `ledgerId`.

Behaviour changes:
- `createGame`/`resetGame` throw for an unknown seed.
- `resolveEvent` no longer emits `bigProject` / `loanOffered` / `lateClient`. They come from the transition that shows the card.
- `getCurrentEvent` hides E5 when the gap is closed.

## Open points
1. **The fraud reveal on 23 XII has no engine event type.** §6 has none. The UI can find the fraud payment in the drilldown (L08 with `eventId: "E1"`) and the re-payment row `E1`. A dedicated `fraudRevealed` narration signal would change the `EngineEvent` union and `reactions.json`, which is an interface change. That is for the coordinator to decide.
2. The UI must route `/gra/1?seed=<x>` for an unknown seed: catch `unknown_seed`, or start `demo`.
3. E5 can disappear in the middle of T5 when the player closes the gap first, for example with C6 or C5. It is then never resolved, by design, and `resolveWeek` does not require it.
4. With E1 `pay_as_is`, the known-ledger forecast does not show the coming crash before T6. So E5 stays hidden in T5 for that path when C1 was played. This follows from "the E5 condition checks the known ledger".
