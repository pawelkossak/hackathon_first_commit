# E-07: Cash Flow series and transactions for the drilldown (G12/G30/G32)

## Built
- `engine/cashflow.ts` (new, internal). It holds pure helpers over forecast series and has no booking logic of its own:
  - `baselineCore`: the state with no card played;
  - `seriesMinimum`, `compareSeries` / `compareForecasts`, `settledThrough`, `buildTasks`.
- `engine/forecast.ts`: the daily run moved into an internal `runSeries`, and the pipeline itself is unchanged.
  - `computeForecast` runs it once for the state.
  - When a card has been played, it runs it a second time for the „Bez działania” baseline. That run uses the same events, choices and week, with no card played: invoice state and overdraft limit go back to their lap-start values.
  - It then adds the drilldown fields.
- `engine/index.ts` `previewCard`: it adds `comparison`, which is `before` → `after`.
- The hidden fraud (E-06) is respected. The baseline, the comparison and the tasks all come from the player-facing view (`groundTruth: false`), so no E1 row or L08 `eventId: "E1"` marker appears before T6.

## Field list for the ui lane (all additive, all numbers engine-computed)
`ForecastPoint` gains:
- `week: WeekNumber | null`: null on 21–22 XI;
- `openingBalance`: the previous end of day, 38 000 on 21 XI;
- `inflow`: ≥ 0;
- `outflow`: ≤ 0, signed;
- `change`: inflow + outflow.

The existing fields are unchanged: `date`, `balance`, `transactions` (inflows first), `counterfactual`.

`Forecast` (from `forecast(state)`, the committed scenario „Po zatwierdzeniu”) gains:
- `minimum: CashFlowMinimum`, which is `{ date, balance, counterfactual }`. It is the lowest lap balance, crash or not, and it is the storm marker.
- `committedCards: CardId[]`: the cards included, in play order. Empty means this forecast is its own baseline.
- `baseline: CashFlowSeries`, which is `{ points, weekEnds, crash, minimum, endBalance, overdraftLimit, afterLap }`. It is „Bez działania”; its `endBalance` is counterfactual when `crash` is set.
- `vsBaseline: CashFlowComparison`, which is baseline (`before`) → committed (`after`).
- `tasks: CashFlowTask[]` („Zadania”). Each row is a `Transaction` plus `counterpartyName`, `week`, `balanceAfter` and `status`:
  - `booked`: in a week already settled;
  - `upcoming`: not settled yet;
  - `rejected`: the crash transaction;
  - `stopped`: after the crash, labelled „Prognoza bez działania”.
- `afterLap: Transaction[]`: transactions after 10 I, which do not appear on the chart. Examples are C5-R on 20 I (−17 400) and L11 moved to 22 I by E6.

`CardPreview` (from `previewCard`, G32 „Przed decyzją / Po decyzji”) gains `comparison: CashFlowComparison`.

`CashFlowComparison` is `{ days, before, after, added, removed }`:
- `days[]` holds `{ date, week, before, after, delta, beforeCounterfactual, afterCounterfactual }`;
- `before` and `after` are each a `CashFlowSummary`: `{ minimum, crash, endBalance }`;
- `added` and `removed` are the transactions that differ, any date. They are matched on id + date + amount, so a moved row shows as removed + added.

UI recipes, all lookups with no arithmetic:
- Week node → date: the week `start` from `gameData.level1.weeks`.
- Chart lines: `baseline.points` (grey), `previewCard(..).after.points` (dashed preview), `forecast(state).points` (committed).
- 28 XII node: `vsBaseline.days` at `2026-12-28`.
- Transaction list: `points[i].transactions`, or `tasks` filtered by date.

## API changes
No signature changes and no new exported functions. The type additions are additive:
- `ForecastPoint` and `Forecast` gain new fields;
- `CardPreview` gains `comparison`;
- the new exported types are `CashFlowMinimum`, `CashFlowSummary`, `CashFlowSeries`, `CashFlowDay`, `CashFlowComparison`, `CashFlowTask` and `CashFlowTaskStatus`.

Any hand-written `Forecast` / `ForecastPoint` fixture in another lane must add the new fields. The typecheck of the repo is green today.

Test update: in `events.test.ts`, ET-E08 now compares the committed forecast without `baseline` / `vsBaseline`. The reason is that the no-card baseline does see the E6 delay once E6 is resolved (INV-A1 is pending without a card). That is intended.

## Open points
1. Each forecast runs the daily series twice once a card is played. This is negligible at 51 days, and the measured forecast + preview time is far below 200 ms.
2. The C1 path in the demo goes through `negotiate`, which is still a fixture (E-08). Until E-08 is done, the tests play C1 directly. E-08 must keep calling `playCard`/`applyCard` so that `committedCards` contains C1.
3. Task status `booked` relies on `weeksResolved`. A week that is played but not yet resolved shows `upcoming`.
